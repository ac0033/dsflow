# 用户报告：在技术讲解中说明业务结果

## 职责与读者

用户报告回答：本步对什么业务问题做了什么、为什么采用这个技术处理、得到了什么结果、这些结果在业务上意味着什么、后续怎样使用。技术和业务在同一条逻辑线上讲，不拆成互不相干的“技术章节”和“业务章节”。用户不懂某个术语时，紧接真实字段、记录或计算例子用大白话说明，之后仍沿用原名称。

开头直接给本步完成状态、最重要的业务结果和下一落点；紧接对象、分母、期间或适用范围，避免一句孤立数字。正文按一至三个读者真正要回答的问题推进，而非按脚本运行顺序、字段清单或图表目录推进。每节先说问题与发现，再用必要的技术原理、操作和真实执行结果解释发现如何产生，以及业务判断因此怎样改变。标题尽量表达结论或要回答的问题；前后段之间要有明确的因果、比较或依赖关系。同一结论只说一次，后文补证据而不反复改写结论。

技术只讲足以理解结果的原理、关键操作和变化，不抄全量代码、参数、哈希、检查清单和失败日志。业务解释包含两层：一是把指标、分布、误差或数据变化对应到实际业务对象与决策；二是用不懂技术的人能复述的话说明“这个数代表什么、不能代表什么、为什么在意”。不要把相关系数、模型分数或检查通过直接写成业务收益。影响使用决定的限制用一两句讲清；详细假设、反例、验证方法、未覆盖项和边界放验收报告。真实不确定性不能为了易读而隐去。

## 参考 Quarto 编排组件

对有代码、表格或图像的步骤，优先交付可渲染的 Quarto 源文件（.qmd）和经过检查的渲染版（通常为 HTML）；保留项目已有报告文件名与格式约定。Quarto 不可用时，可交付同样编排的 Markdown 加真实输出与图像，明示没有完成 Quarto 渲染，不能把静态片段称为已执行的代码单元。

在一个问题的小节内，让组件紧挨其解释：提出要核对的业务问题 → 放必要的真实代码片段或处理规则 → 放实际执行得到的数字、表或图 → 立刻解释其业务含义和后续用途。不是每节都必须有代码和图；只保留能帮助读者理解操作或验证结论的组件。完整脚本与全部结果在实际产物中链接，不把用户报告写成 notebook 输出堆栈。

若使用 .qmd，可把关键代码单元与输出相邻展示；长代码折叠或隐藏，图表给说明性标题、图注和替代文本，并在正文引用。数字可由已核实的计算结果动态插入，避免手工复制后与图表不一致。执行代码单元、静态展示的代码片段和外部产物要明确区分；不得给未运行代码配上冒充执行结果的表或图。渲染后检查标题层级、表格可读性、图像清晰度、代码与输出位置、数值一致性和链接有效性。

需要学习同类报告写法时，优先看项目已有优秀报告，再参考一至两篇公开的 Quarto 实例，借鉴“问题—代码/结果—解释”的布局、图表说明和层次，不照搬别人的结论或数据。例如 [Quarto 计算文档教程](https://quarto.org/docs/get-started/computations/rstudio)、[Quarto 图表与布局](https://quarto.org/docs/authoring/figures-and-layout.html)、[苏黎世大学 Python 动态报告示例](https://crsuzh.pages.uzh.ch/cas-unil-data-stewardship-2026/Dynamic_reporting_exercise/index_py.html)。

## 交付前的读者检查

仅读用户报告，读者应能按顺序说清：输入的业务对象是什么 → 技术如何把输入变成结果 → 指标对应的业务含义是什么 → 本步支持哪一个判断。涉及变换或关联时，给一个真实且可核对的最小例子，走完输入记录、关键处理、输出记录与对应产物；虚构例子必须明示。每个主要图表和代码块都应有正文解释，且删掉任一组件不会留下无法理解的跳步。主 agent 用实际产物复核用户报告数字，并以独立读者视角检查是否需要读验收报告才能理解正文。
