# EDA 用户报告：从发现走向业务问题

仅在探索性数据分析（EDA）阶段使用。通用的[用户报告写法](user-report.md)决定叙事与 Quarto 式组件编排；详细核验和证据边界由[验收报告](acceptance-report.md)承担。本文件帮助把宽范围扫描收束为读者能理解、后续能验证的问题，不规定必须做哪些统计或写满哪些章节。

## 先选真正影响判断的发现

EDA 要回答的是数据覆盖哪些业务对象，目标或关键业务结果如何分布，哪些关系值得进一步查证。数据质量若已在前一步验收，只引用会影响本次发现的部分，不重复整张检查表。正文挑一至几个改变理解的结果：选择依据可为业务关联、规模、分组差异、稳定性或异常，而非只按相关系数绝对值排序；完整指标扫描仍保存在结构化产物与验收报告，防止只展示好看的结果。

每个小节从一个业务问题或读者疑问出发，紧接实际图表、执行结果或必要的代码片段，再用原始字段和大白话说明指标在这批业务对象中代表什么。若分析先看总体再看分组或敏感性，解释为什么后一步能回答前一步留下的问题；不把“单变量、双变量、多变量”或“读取数据、画图、算相关”当作用户报告的机械目录。

## 把技术结果翻成业务可理解的话

不能只写“正相关”“提升 0.02”或“图中可见”。说清比较的是哪些行或对象、分母和单位，技术指标实际回答了哪一个问题，数值变化对应的业务大小和后续用途。对于相关系数，先用同一数据中的可核对分组或记录帮助理解，再说明它是观察关系，不是提高某指标就能改变业务结果。对于小样本、零结果、反向结果或分组后关系变化，照实写它怎样改变原判断。

用户报告只简短指出会影响读者行动的限制，例如缺少关键字段使结果不能用于因果决策；采样、替代解释、多重比较、重复行处理和未覆盖检查的完整讨论放验收报告。若现有数据无法稳定区分解释，不为填满报告继续切分或制造建议，说明尚不能支持哪项决策，以及下一步需要什么证据。

每张重要图应回答一个问题，标题或图旁文字点出观察结果，正文说明它为什么重要；不是给图编号后让用户自己找结论。代码、图、表、正文相邻，不让读者来回翻页才能拼出推理。
