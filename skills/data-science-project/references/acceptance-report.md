# 验收报告：记录为什么能通过

## 职责与结论

验收报告由主 agent 在执行 agent 交付后写，目的是让人能够追溯“验了什么、怎样验、结果如何、证据能支持到哪里”。执行 agent 的自检和运行成功是待核证材料，不是主 agent 的独立验收。开头直接写通过、部分通过或失败，以及可否进入下一步；分别判断技术实现、理论解释和业务适用范围。计划中的验收标准逐项给结论，未验或失败不写成通过。

## 从真实输入到验收判断

记录本步目标、批准计划和输入版本；对原始数据及关键依赖产物保留路径、大小、哈希或项目已有的可信版本标识。按重要性说明实际代码与产物怎样对应，关键行、字段、对象、分布或模型指标如何变化，主 agent 从哪里重新读取并核对。复杂变换至少给一个真实记录的输入 → 规则/操作 → 输出 → 产物位置，让别的复核者能重走结论。

验收方法要说到足以重做：全量还是抽样、独立重算还是代码审查、对照来源与容差、检查器是否做过能触发失败的故障注入。执行者同一函数再跑一次只算复现，不称独立核证。保留通过的关键数字、失败和修正尝试、差异原因；代码运行、图像渲染或检查器全绿都不能单独证明业务正确。

单独说明事实、推断、假设与未知，解释结果在哪些对象、时间、场景中适用，哪些因素限制推广、因果或上线使用。列出未覆盖的检查、剩余风险、需要业务确认的口径，以及它们是否影响放行。本步不通过时点明受影响产物和返回位置，交执行 agent 修正并复验；通过时说明产物可如何用于下一步，但仍等用户理解且同意。

验收报告可用表格汇总“验收标准—核对方法—实际结果—判定”，但不要让表格取代关键判断的推理。详细日志与全量检查结果就近链接，正文保留判断所需的证据。用户报告只需链接这份验收报告，并简述影响业务使用的关键限制。
