# 计划与执行补充

## 开工前先检查环境

写第一份计划之前，先确认代码要跑的那个 Python 环境已经建好：解释器在哪、后面要用的库能不能真的 import 进来、项目约定的记录工具（接入 DSFlow 时是 `dsflow`）在不在这个环境里。接入 DSFlow 的项目调 `env_check`（缺什么用 `env_prepare` 或 `dsflow attach <项目目录> --venv` 补齐），没有平台时在项目自己的环境里把计划要用的库 import 一遍。计划里写明代码在哪个环境里跑、额外装了什么库、为什么要它。环境缺一半时，要到执行那一刻才报错，那时计划已经批过、时间已经花掉，只能退回重做。

## 从决定反推计划

先用一句话说清**本步结束后用户要知道、判断或使用什么**。从这个目的反推当前缺口，选能回答缺口的证据，再决定处理动作与产物；不按工具、图表或字段顺序拼待办。较长的计划可按下表思考，不要求照抄为标题：

| 要回答的问题 | 现有输入与未知 | 拟取证据和处理 | 产物及后续用途 | 验收与停点 |
|---|---|---|---|---|
| 一个必要的判断 | 数据范围、粒度、版本、关键假设 | 为什么这些操作足以回答问题 | 实际拟生成文件如何供下一步使用 | 什么证据算通过，什么冲突使本步暂停 |

问题之间按依赖排序：先确认数据和口径，才能比较；先确定预测时点和切分，才能评估模型。每一项操作都能回到某个问题；若不能，就删掉或列为另一步。区分“本步能回答什么”与“本步仍不能判断什么”，避免计划写成预设结论。对简单步骤只写目的、输入与动作、产物、验收/停点即可，不强加表格。

例如，若本步目的是判断两份原始葡萄酒 CSV 是否足以开展探索分析，计划先问“每行和 quality 代表什么、有没有会使计数失真的问题”，再安排核对字段、行数、缺失、重复行并保存数据概况；验收要求原始指纹不变、关键频数可独立复核。计划不能先写“重复行应删除”或“某指标有效”，因为这两项尚无证据，也不属于该目的。

## 计划写到可以执行和评估

**一步是一个完整独立的单元**：它有自己的输入、自己的产物、自己能核对的验收标准，做完能单独讲给用户听。两个问题都答「能」才算一步：这一步的产物能不能被下一步直接使用？验收标准能不能只看本步产物核对？答「不能」就合并或者拆开。把一个阶段的操作全堆在一步里，用户在中间没法评估，出问题要整步重做；把一个操作拆成三步（读文件一步、改列名一步、存盘一步），每一步都没有能交付的产物，评估和验收就空转。

计划围绕一个完整业务目的，可包含必要的多项操作。写清业务问题与假设、输入版本、操作和依据、产物及用途、验收标准、依赖、范围与停止条件；不要把每个函数拆成一步。执行说明与用户说明可以分层或按项目约定分文件，实质内容必须一致。

主 agent 制定计划 → 用户评估同意 → 执行 agent 执行并起草用户报告 → 主 agent 从产物独立核验并写验收报告 → 审阅交付用户报告 → 用户理解且同意 → 下一步计划。默认这两个角色是同一个 agent：同一个会话依次走完五个环节；用户明确安排了独立的执行 agent 时才分开。兼任时验收仍要从实际产物重新核对，不复用执行时的中间结果。

返回修正时复用原步骤的新轮次，保留历史；先说明哪些后续步骤受影响及依据，只重做必要部分，修正后回到实际推进位置。

## 建模与实验

训练前确定业务目标、预测时点、标签、数据切分、基线和评价指标，并提出可检验的假设。工具、模型和参数由 agent 在批准范围内选择，说明理论依据与业务取舍。

用于归因的对照只改变一个因素；多因素实验先说明设计及归因限制。记录必要参数和所有有意义的尝试，比较基线、候选及差值；有交叉验证时保留逐折结果。小幅提升要结合波动与样本限制解释。

最终评估数据不得用于训练、调参、特征选择或方向决策。填补、缩放、编码等需要从数据估计的参数只在训练部分拟合；时间相关字段和关系必须在预测时点可获取。

## 保留可复现的工作

沿用现有目录，保留产物、代码、日志、验收报告和用户报告及其对应关系；日志记录输入版本、运行入口、必要环境与参数、结果和失败原因即可。原始数据与历史结果不覆盖，版本快照按项目要求执行。交付用于业务运行时，补齐运行入口、适用范围和必要的失败处理。
