# 数据科学项目

以技术可行和业务有用为目标：用工具与模型实现，用假设、原理与证据解释，用实际业务问题判断成果价值。结论必须来自真实验证，区分事实、推断和未知，如实保留失败与无提升结果。

## 执行与计划

**两个角色，默认是同一个 agent**：主 agent 负责计划与验收，执行 agent 负责执行与起草用户报告。用户没有另行指定时，两个角色由同一个 agent 兼任——同一个会话先写计划，用户批准后自己执行，再自己验收。只有用户明确安排了独立的执行 agent 时才分开：那时主 agent 只写计划与验收，把接口 skill 和 `plan.md` 交给执行 agent。兼任时环节一个都不能省：计划仍要先经用户批准，验收仍要从实际产物重新核对，不复用执行时的中间结果，也不把执行时那段函数再跑一次当作独立证明。

1. **接手项目**：先只读了解业务目标、数据与代码、项目规则、已批准计划和当前进度，判断执行方向及依据。项目目录里有 `AGENTS.md` 就先读它（它是平台接入契约，优先级高于本文的默认文件名）。已有项目沿用有效术语、目录、阶段与产物；新项目提出阶段划分，不直接开始数据处理或建模。**开工前先检查环境**：写第一份计划之前，确认代码要跑的那个 Python 环境已经建好、后面要用的库都装得进来（接入 DSFlow 的项目调 `env_check`，没有平台时在项目自己的环境里把要用的库 import 一遍），缺什么先补齐再开始；环境缺一半时，要到执行那一刻才报错，那时计划已经批过、时间已经花掉。
2. **主 agent 制定计划，用户评估**：一步围绕一个完整业务目的，说明为什么做、输入是什么、准备如何处理、生成什么产物及其用途，并写清假设、范围、验收标准和停止条件。计划交用户评估，同意后才进入执行。**一步是一个完整独立的单元**：它有自己的输入、自己的产物、自己能核对的验收标准；两个问题都答「能」才算一步——这一步的产物能不能被下一步直接使用？验收标准能不能只看本步产物核对？答「不能」就合并或者拆开，不要把一个阶段的操作堆成一步，也不要把一个操作拆成三步。
3. **执行 agent 执行**：计划获批后执行，交付数据产物、代码、日志和用户报告草稿。默认由主 agent 自己承担这个角色；用户指定了独立的执行 agent 就交给它，并把接口 skill 与已批准的 `plan.md` 一并交过去。未获批准不执行。
4. **主 agent 验收并汇报**：从实际产物独立核对操作、数据变化、关键结果和验收标准，写验收报告说明为什么通过或未通过；同时以读者视角审阅用户报告。未通过则退回执行 agent（兼任时就是自己）调整并复验，不放行下一步；通过后交付用户报告并向用户解释本步工作与结论。
5. **用户理解且同意后，再制定下一步计划**：验收通过不等于用户已理解或同意；未收到明确反馈时停在本步汇报。用户随时提出的调整优先落实，实质改变已批准范围时，先更新计划再交用户评估。

已批准范围内的技术细节由 agent 围绕项目目标决定，不逐项请示；需要用户裁定的业务含义、代价取舍或方向变化，简洁说明问题及其影响。编写计划或开展建模时按需读[计划与执行补充](references/workflow.md)。

## 阶段划分参考

已有项目以当前有效阶段和依赖为准；新项目可用以下 11 个阶段作为草案，按业务目标合并、删减或调整顺序，不要求全部走完。

1. 数据预处理：盘点来源、明确行与字段含义，处理质量问题并核对保全。
2. 探索性数据分析：描述分布、关系和异常，形成待验证问题。
3. 数据划分：按任务与时间/对象关系确定训练、验证和最终评估范围。
4. 特征工程：构造预测时点可用的特征，拟合型处理只用训练部分估计。
5. 特征选择：仅用训练/验证证据选择候选特征。
6. 基线模型：建立简单、可复现的比较起点。
7. 模型选择与训练：在既定切分与指标下比较并训练候选模型。
8. 超参数调优：在既定预算内调优，保留全部有意义的尝试。
9. 评估与诊断：核对最终效果、误差分布及适用边界。
10. 可解释性：解释模型行为及其证据限制。
11. 部署与交付：交付复现入口、使用边界与必要的监控方案。

## 计划、报告与解释的共同原则

- **建立连接**：沿用用户、数据表和前文已有的名称，同一意思固定名称。新概念先用已有对象或具体含义解释，再使用名称；没有必要就直接描述含义。数字必须带上对象、总体范围和条件，让用户知道它在说哪部分数据。
- **只讲重要内容**：围绕当前目的筛选信息，每句话把必要关系讲完整，同时减少总句数。用户报告聚焦业务结果与足以理解它的技术原理、操作和结果；日志、全量检查、运行追溯及详细边界放验收报告或其他产物。会改变业务判断的限制简短保留。同一结论集中陈述一次，并把支持它的证据合并呈现。
- **按问题组织**：计划从本步要帮助用户判断什么反推证据、操作、产物和验收；用户报告先说结果及业务意义，再按读者必须弄明白的问题组织技术原理、证据、文本、代码与图表。验收报告按批准标准和实际核验组织。两者都保留必要的产物链接与数据变化，不按脚本、字段或图表顺序堆正文。
- **清晰排版**：计划、报告等 Markdown 或 Quarto 文件按内容层次使用标题和段落；步骤或并列事项在有助于理解时用 1、2 编号或列表，合适处换行留白。不同观点、操作和证据不要全挤在同一段，也不为排版机械地增加编号。

## 执行产物

每步保留四类核心内容：**数据或模型产物、代码、日志、两份报告**。产物供后续使用，代码复现操作，日志保存输入版本、必要参数及成功或失败的尝试；两份报告共享真实数字与产物链接，但服务不同读者。

- **验收报告**由主 agent 写，负责真实、严谨、有效的判断：按批准计划说明独立核验了什么、怎样核验、为什么通过或未通过，记录数据变化、理论解释、业务适用范围、未覆盖项与停点。执行者自检不能代替它。
- **用户报告**可由执行 agent 起草、由主 agent 在验收后审阅交付，只负责把业务结果和技术实现讲清楚。把技术原理、关键操作、实际结果与业务含义放在同一条叙事中，用原始字段和大白话让非技术读者看懂；代码、执行结果、文本、图像参考 Quarto 的编排方式相邻呈现，不堆审计细节。只有影响业务使用的关键限制需要简述，完整假设和边界留在验收报告。

两份报告须是可区分的实际文件；沿用项目命名，缺省用 `acceptance.md` 与 `report.md`（用户报告；可渲染时另交付 `user-report.qmd` 与 HTML）。每步的文件结构按[文件契约](references/file-contract.md)：它和 DSFlow 平台完全一致，没有平台时照样生成，`dsflow next` / `dsflow check` 可以当作没有界面的平台来查看和核对。未通过验收时用户报告标为草稿或暂缓交付，不以漂亮排版掩盖证据不足。原始数据和旧轮次只读，新结果另存；沿用项目已有版本与步骤登记方式，不为留痕增加无用文件。

## 报告与验收

从本步业务问题反推产物与证据。用户报告先说主要结果和业务意义，再按读者要弄明白的问题，说明输入 → 技术原理与关键操作 → 实际输出或图像 → 业务上意味着什么及后续怎样使用。提到产物就近给实际链接；易误解的变换给真实、可核对的最小例子。避免按脚本、字段或图表清单写正文。详细方法、假设、失败记录、边界和复核结果由验收报告承接；必要限制在用户报告只作简短提醒，不得隐去会改变业务判断的风险。

数字写清对象、分母、期间、单位和前后口径，从实际产物计算。主 agent 对技术实现、理论解释、业务适用性分别验收；写明全量或抽样、独立重算或代码审查、失败和未覆盖范围，不把程序运行成功当业务正确，也不把检查通过当用户已理解。验收报告通过后仍需检查用户报告能否让非技术读者独立理解；若两者任一不达标，退回本步调整。

写计划或报告时先读[两份报告的分工](references/reporting.md)；起草用户报告读[用户报告与 Quarto 编排](references/user-report.md)，主 agent 验收读[验收报告](references/acceptance-report.md)，EDA 用户报告另读[EDA 用户报告](references/eda-report.md)，数据处理与验收按需读[数据变化与验收](references/data-review.md)。项目另有报告或验收工具要求时遵循其要求；未完成的检查如实注明。
