# 讲解写法：一句话要能单独看懂

读者是懂业务、能读代码、没做过数据科学的负责人。讲解里的每一句话，读者不看代码、不看上下文也要知道**对什么、做了什么、结果是什么**。平台的 `dsflow guide lint`（以及项目里挂的 hook）按下面的规则机械检查，不通过就退回。

## 为什么会写成缩略语

缩略语是讲解里反复出现的毛病，靠"注意一点"拦不住，只能靠去掉触发条件再加机械检查。三个触发条件：

1. **字数上限 + "一句话"的要求**。写到字数上限时，最先被砍掉的就是宾语和限定语，于是「先把 3.1 的划分表和基线核对一遍」被压成「先把 3.1 的划分和基线对上」。所以体检的字数上限只防堆砌，下限反过来逼出完整的句子。
2. **"白话"被理解成了口语**。要求"用白话"时，写出来的是工程师自言自语的口头语（对上、合上、钉死、站住、跑通），这些词只有写代码的人自己知道指什么。白话应该是**完整的书面句子，不用术语**，不是省略。
3. **用抽象名词代替具体对象**（"把划分和基线对上"里的"划分"其实是"划分表里的三份行数"）。作者脑子里有具体对象，写的时候只写了类别。

## 规则（体检逐条检查）

1. **每句完整**：主语（或明确的承前对象）+ 动词 + 宾语 + 结果。每个字段以句号、问号或叹号结尾。
2. **动词带宾语，宾语是具体对象**：数据表名、列名、文件名、术语表里的词或数字。「做什么」「输出结果讲解」里必须至少点名一个具体对象。
3. **不用口语缩略动词**。下面这些词一出现就退回，右边是该怎么写：

   | 不许写 | 要写成 |
   |---|---|
   | 对上、对账 | 核对 A 与 B 是否一致 |
   | 合上 | 按 X 列把 A 表和 B 表合并 |
   | 钉死、定死、写死 | 固定 X，不再改动 |
   | 押在、靠 X | 主要依赖 X |
   | 压下去 | 把 X 降低到 Y |
   | 站住、站得住、站不住 | 在 X 上仍然成立 / 不再成立 |
   | 跑通 | 成功执行并得到 X |
   | 露出、摊开 | 显示 X、逐项列出 X |
   | 抹掉、堵住、兜住、撑着 | 去掉 X、防止 X、由 X 支撑 |
   | 挑出来、拍板 | 选出 X、决定 X |
   | 落到、带进、挂上 | 写入 X、记录到 X、关联到 X |
   | 上场、碰、偷看 | 参与 X、使用 X、使用了不该用的 X |
   | 必输、赢在、一路成立 | 误差一定高于 X、在 X 上误差更低、在每个分组都成立 |
   | 换一把尺子、同一把尺子 | 换一种评价方法、同一种评价方法 |

4. **抽象词要么登记要么不用**：口径、主线、闭环、落盘、地基、裁判这类词，没在术语表里解释过就不能出现。
5. **长度是下限不是上限**：「做什么」「为什么」至少 18 字，「输出结果讲解」至少 60 字——它要指着输出里的具体数字讲：这个数是什么、和预期或上一步比怎么样、说明了什么。上限放宽到 120 / 140 / 400 字，够写完整的句子。
6. 开头六段每段一句完整的话；结论最多一个数字；操作不写数字；**结果**写做完留下了哪些核心产出、它们现在能干什么，要和目的、操作对得上（例：把 2,285,030 行的订单行基表落到 data/interim/orders_line.parquet，后面每一步都直接读它）。

## 好句子长什么样

- 差：先把 3.1 的划分和基线对上。
- 好：先按源文件行号把每条原始行和 3.1 的划分表合并，只保留训练行和验证行；再用训练行的 quality 中位数重算基线，核对它的验证集 MAE 与 3.1 保存的结果是否一致。
- 差：随机森林把平均差压下去了。
- 好：随机森林把红酒验证集的 MAE 从基线的 0.6435 降到 0.5051，平均每份酒的评分误差少了 0.14 分。
