# 1.2 订单清洗

**结论**：订单明细从 121,000 行清洗为 119,998 行，只删了两类行：完全重复的 1,000 行、下单时间在数据截止月之后的 2 行。其余订单行的数量与金额一个没改，可以直接用于 2.1 看需求分布、3.1 构造 SKU×月面板。

本步处理的对象是 `data/raw/orders.csv` 的全部订单行（下单时间 2024-07 至 2026-06，一行 = 一个订单号下的一个 SKU）。1.1 已经数清楚有哪些质量问题，这一步决定每类问题怎么处理，并保证处理前后能逐行对账。

## 删掉了哪些行，为什么只删这两类？

判断标准只有一条：这一行留下来，会不会让需求量算错。

- 完全重复行：12 个字段全都一样，多出来的那一行会把同一笔需求算两次，所以删。
- 未来日期：下单时间是 2027-01-05，落在数据截止月 2026-06 之后，既不属于训练，也不属于评估，所以删。

**操作**：真正起作用的就是这几行（摘自 [nb_1.2.ipynb](nb_1.2.ipynb) 第 3 格，逐格讲解见「讲解」）：

```python
dedup = raw.drop_duplicates()                     # 所有字段都相同的行只留第一行
placed = pd.to_datetime(dedup["下单时间"])
future = placed > f"{LAST_MONTH}-30 23:59:59"     # LAST_MONTH = 2026-06
clean = dedup[~future].copy()
```

执行结果写在行数台账 [outputs/row_ledger.csv](outputs/row_ledger.csv)：

| 处理 | 行数 |
|---|---:|
| 原始 | 121,000 |
| 删除完全重复行 | 1,000 |
| 删除未来日期 | 2 |
| 清洗后 | 119,998 |

121,000 − 1,000 − 2 = 119,998，台账逐行对得上；说明卡上的这几个数字，平台已经从台账重算核对过。

**例子**：订单号 SO202701000000，下单时间 2027-01-05 00:00:00，SKU02343，数量 1。它晚于 2026-06-30，属于"删除未来日期 2 行"中的一行；清洗后的 [orders_clean.parquet](outputs/orders_clean.parquet) 里查不到这个订单号。

## 退货行和金额缺失的行为什么不删？

它们仍是真实发生的订单行，删掉会丢信息；算不算需求量是口径问题，留给 2.1 决定。所以这一步只加标记、不改数值：

- 退货行：数量为负的 361 行，加一列「是否退货」= true。
- 金额未知：金额为空的 636 行，加一列「金额未知」= true。本项目预测的是数量，金额空着不影响需求量。

**例子**：订单号 SO202407060071，SKU02380，数量 −6，金额 −2209.68。它留在清洗结果里，「是否退货」= true；2.1 算需求量时会把这类行排除。

**注意**：1.1 在原始文件里数到金额缺失 641 行、数量为负 364 行，清洗后是 636 和 361。差的 5 行和 3 行都在删掉的 1,002 行里——它们本身就是重复行或未来日期行。

## 商品名称做了什么？

1.1 数到原始文件里有 3,733 个订单行的商品名称带首尾空白或全角字符。这里统一全角 / 半角并去掉首尾空白。

**例子**：订单号 SO202407013742（SKU00136）的商品名称是「Ａ４复印纸 加厚56型　」——全角的 Ａ４，结尾还有一个全角空格；处理后是「A4复印纸 加厚56型」。

本项目按 SKU 统计，商品名称不参与计算；统一名称只是为了以后按名称查找时不漏。

## 这对后面意味着什么？

**业务含义**：清洗后，每个订单行只出现一次，下单时间都落在 2024-07 至 2026-06。非退货订单行的数量合计是 547,214——2.1 的各类目月度需求量、3.1 的 SKU×月面板加起来都必须等于这个数，它是后面所有需求量的对账基准。

**下一步**：2.1 确定需求量口径并看季节性；3.1 按时间切分。
